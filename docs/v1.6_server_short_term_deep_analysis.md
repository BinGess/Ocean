# v1.6 深入分析服务端短期改造说明

> 更新时间：2026-06-13  
> 适用分支：`v1.6`  
> 目标读者：服务端同事  
> 范围：只覆盖短期必须做的协议与存储兼容，不包含 Coze 智能体服务端代理迁移。

## 1. 背景

v1.6 客户端已经接入新的深入分析链路：

1. NVC 智能体会在原有 NVC 四模块之外，额外返回一个推荐深入分析方法。
2. Pro 用户可以对同一条记录生成一条或多条深入分析结果。
3. 深入分析结果目前先存在客户端本地 Hive，暂时不能跨设备同步。

短期服务端不需要负责生成深入分析内容，也不需要调用 Coze。服务端需要先完成两件事：

1. Record 的 `nvc` 对象允许透传 `recommendedMethod`。
2. Record 支持保存和同步 `deepAnalyses` 数组。

## 2. 本次服务端要做什么

### P0：透传 `nvc.recommendedMethod`

客户端保存 Record 时，`nvc` 对象里会多一个可选字段：

```json
{
  "nvc": {
    "observation": "今天和同事沟通时有点委屈",
    "feelings": [],
    "needs": [],
    "request": "我想先把自己的感受说清楚",
    "insight": "你很在意被理解",
    "recommendedMethod": "boundarySupport",
    "analyzedAt": "2026-06-13T12:00:00.000+08:00"
  }
}
```

服务端需要：

1. 创建、更新 Record 时允许该字段存在。
2. 列表、详情、全量同步、增量同步接口原样返回该字段。
3. 旧记录没有该字段时返回 `null` 或直接缺省均可，客户端可以兼容。
4. 旧客户端上传的 `nvc` 不含该字段时，不要因为字段缺失导致异常。

字段枚举值：

| 值 | 含义 |
| --- | --- |
| `cognitiveReframe` | 想法校准，CBT |
| `releaseControl` | 放下控制，ACT |
| `selfCompassion` | 自我关怀与滋养，Self-Compassion & Savoring |
| `boundarySupport` | 稳住情绪，DBT |
| `gentleRecovery` | 慢慢带回自己，Behavioral Activation |

建议校验策略：短期可以只做字符串透传；如果服务端要校验枚举，遇到未知值建议保存为 `null` 或返回明确 400，避免静默写入脏数据。

### P1：Record 增加 `deepAnalyses`

Record 顶层新增可选数组字段：

```json
{
  "deepAnalyses": [
    {
      "type": "selfCompassion",
      "title": "自我关怀与滋养",
      "methodLabel": "Self-Compassion & Savoring",
      "theorySource": "源自自我关怀与正向心理学",
      "overview": "难受时，陪你停止自我攻击；美好时，帮你把这份好放大、留住。",
      "stuckPoint": "是不是我不够好",
      "groundedUnderstanding": "这不是你这个人的问题，而是你正在经历一段很难的关系感受。",
      "oneSmallStep": "把手放在胸口，慢慢呼吸三次。",
      "steadySentence": "我可以先不责怪自己。",
      "analyzedAt": "2026-06-13T12:10:00.000+08:00",
      "face": "low",
      "enoughSignal": true,
      "resonance": "这件事让你一下子把责任都揽到自己身上了。",
      "emotions": [
        { "name": "委屈", "intensity": 80 },
        { "name": "自责", "intensity": 65 }
      ],
      "observedLabel": "你对自己说的话",
      "observedValue": "是不是我不够好",
      "truthLabel": "但其实",
      "truthValue": "关系里的反应不等于你这个人的价值。",
      "microActionKind": "self_kindness"
    }
  ]
}
```

服务端需要：

1. Record 创建接口接收并保存可选 `deepAnalyses`。
2. Record 更新接口接收并保存可选 `deepAnalyses`。
3. Record 列表、详情、全量同步、增量同步接口返回 `deepAnalyses`。
4. 删除 Record 时无需单独处理子资源，随 Record 一起删除即可。
5. 旧记录允许 `deepAnalyses` 缺失、为 `null` 或为空数组。

建议返回策略：没有深入分析时优先返回空数组 `[]`，也可以缺省；客户端会兼容。

## 3. `deepAnalyses` 字段说明

### 必填字段

这些字段是旧版四卡结构已经存在的字段，建议服务端保存时要求存在：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `type` | string | 深入分析方法，枚举同上 |
| `title` | string | 页面标题 |
| `methodLabel` | string | 方法英文/学派标签 |
| `theorySource` | string | 理论来源 |
| `overview` | string | 方法概述 |
| `stuckPoint` | string | 兼容字段，新结构里通常承载 observed 内容 |
| `groundedUnderstanding` | string | 兼容字段，新结构里承载一句洞察 |
| `oneSmallStep` | string | 微行动文案 |
| `steadySentence` | string | 给自己的一句话 |
| `analyzedAt` | string | ISO 8601 时间 |

### 可选字段

这些是 v1.6 结构化结果新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `face` | string? | 仅 `selfCompassion` 使用，值为 `low` 或 `high` |
| `enoughSignal` | boolean | 输入信息是否足够，缺省可视为 `true` |
| `resonance` | string? | 开口第一句，共鸣句 |
| `emotions` | array | 情绪数组，元素为 `{ "name": string, "intensity": number }` |
| `observedLabel` | string? | 翻转卡上半 label |
| `observedValue` | string? | 翻转卡上半内容 |
| `truthLabel` | string? | 翻转卡下半 label |
| `truthValue` | string? | 翻转卡下半内容 |
| `microActionKind` | string? | 微行动类型 |

`microActionKind` 当前可能值：

| 值 | 说明 |
| --- | --- |
| `self_kindness` | 自我关怀 |
| `savoring` | 品味滋养 |
| `thought_check` | 想法校准 |
| `defusion` | 放下控制 / 认知解离 |
| `steady_express` | 稳定表达边界 |
| `tiny_recharge` | 小步恢复 |

## 4. 兼容规则

### 旧客户端兼容

旧客户端不会上传 `nvc.recommendedMethod` 和 `deepAnalyses`。服务端必须保持旧 payload 可用。

建议：

1. 字段缺失不报错。
2. 更新 Record 时，如果旧客户端没有传 `deepAnalyses`，不要误把已有 `deepAnalyses` 清空，除非当前接口语义本来就是完整覆盖。
3. 如果现有更新接口是整条 Record 覆盖，需要确认客户端版本来源；短期可接受“谁提交谁覆盖”，但要避免服务端因为 schema 过滤导致新字段被丢掉。

### 新客户端兼容

新客户端可能先只上传 `nvc.recommendedMethod`，暂时不上传 `deepAnalyses`，因为当前深入分析仍在本地 Hive。服务端支持字段后，客户端会再接入 `deepAnalyses` 同步。

建议服务端提前支持两种情况：

1. `nvc.recommendedMethod` 存在，但 `deepAnalyses` 缺失。
2. `deepAnalyses` 存在，但为空数组。

## 5. 更新与冲突策略建议

同一条 Record 可以有多条深入分析，不同 `type` 可以并存。同一个 `type` 通常只保留最新一条。

服务端有两种实现方式：

1. 简单方式：把 `deepAnalyses` 当作 Record 的普通 JSON 数组，客户端提交什么就保存什么。
2. 更稳方式：服务端按 `type` 做 upsert，同一 `type` 替换，不同 `type` 追加。

短期推荐简单方式，成本最低，也和当前 Record 整体同步模型更一致。后续如果多设备冲突明显，再升级为服务端按 `type` 合并。

如果已有版本号或 `updatedAt` 冲突机制，`deepAnalyses` 跟随 Record 一起参与即可。

## 6. 接口影响范围

需要检查以下接口或同步链路：

| 场景 | 服务端要求 |
| --- | --- |
| 创建 Record | 接收并保存 `nvc.recommendedMethod`；预留 `deepAnalyses` |
| 更新 Record | 接收并保存 `nvc.recommendedMethod` 与 `deepAnalyses` |
| Record 详情 | 返回 `nvc.recommendedMethod` 与 `deepAnalyses` |
| Record 列表 | 返回 `nvc.recommendedMethod`；如列表本来返回完整 Record，也返回 `deepAnalyses` |
| 全量同步 | 返回两个新字段 |
| 增量同步 | 返回两个新字段 |
| 删除 Record | 随 Record 删除，无需额外接口 |

## 7. 验收用例

### 用例 1：保存并读取 `recommendedMethod`

1. 创建或更新一条 Record，`nvc.recommendedMethod = "boundarySupport"`。
2. 调用详情接口，确认字段原样返回。
3. 调用列表/同步接口，确认字段不丢失。

### 用例 2：旧记录兼容

1. 创建一条不含 `recommendedMethod`、不含 `deepAnalyses` 的旧格式 Record。
2. 确认创建成功。
3. 确认详情和同步接口正常返回，不出现解析错误。

### 用例 3：保存并读取 `deepAnalyses`

1. 更新一条 Record，传入包含一条 `selfCompassion` 的 `deepAnalyses`。
2. 调用详情接口，确认所有字段原样返回，包括 `face`、`emotions`、`observedValue`、`truthValue`。
3. 再传入另一条 `cognitiveReframe`，确认数组可以保存多条结果。

### 用例 4：空数组兼容

1. 更新 Record，`deepAnalyses = []`。
2. 确认接口成功。
3. 确认返回为空数组或缺省，不影响 NVC 字段。

## 8. 暂不需要做的事

短期这轮服务端优化暂不要求：

1. 不需要新增意图分类接口。
2. 不需要服务端生成深入分析。
3. 不需要服务端调用 Coze。
4. 不需要校验 Pro 权益。
5. 不需要解析或改写深入分析文案。

这些属于下一阶段“智能体调用迁移到服务端代理”的范围。
