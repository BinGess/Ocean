# v1.6 深入分析功能改动与前后端协作说明

> 更新时间：2026-06-07
> 分支：`v1.6`
> 用途：说明 v1.6 客户端已经完成的页面与本地数据能力，以及后续需要服务端和智能体补齐的工作。

## 1. 当前结论

v1.6 已经完成“在 NVC 结果之后继续深入”的完整客户端原型和交互链路：

1. 用户先获得原有 NVC 分析结果。
2. NVC 结果页展示 5 种深入分析方法，并推荐其中一种。
3. Pro 用户选择方法后进入深入分析结果页。
4. 深入分析完成后，结果回写到当前 NVC 结果页。
5. 同一条记录可以保存多种深入分析，之后从记录列表重新打开时仍可查看。

目前这条链路可以在本地完整演示，但有两个重要边界：

- **深入分析智能体尚未配置。** 当前推荐逻辑是客户端关键词规则，分析正文是客户端固定模板，不是真实 AI 生成结果。
- **深入分析结果尚未接入服务端。** 当前使用 Hive 按记录 ID 保存在本机，不会跨设备同步。

现有 Record/NVC 服务端协议没有被修改，也没有向服务端发送未知字段。

## 2. 页面层级已经完成的改动

### 2.1 保持不变的页面

- 首页语音输入页的核心流程不变。
- 文字输入页的核心流程不变。
- NVC 分析过程页不变。
- 原有 NVC 的“事实观察、感受、需要、行动 Tips”内容结构不变。

### 2.2 NVC 结果页

原来的 NVC 长浮层改为独立完整页面，并保留原有能力：

- 展示用户原始记录。
- 展示并编辑事实观察、感受、需要和行动 Tips。
- 修改记录时间。
- 已有记录支持分享和删除。
- 顶部导航与系统状态栏使用统一背景，减少割裂感。

NVC 结果下方新增“继续深入”区域：

- 横向滑动展示 5 种方法卡片。
- 卡片显示产品名称和理论来源。
- 根据当前记录推荐一种方法，并自动将推荐项滚动到可视区域。
- 用户先选择方法，再点击底部按钮进入结果页，避免误触后直接跳转。
- 底部左侧为深色主按钮“查看深入分析”，右侧为“完成”。

5 种方法目前为：

| type | 页面名称 | 方法 | 理论来源 |
| --- | --- | --- | --- |
| `cognitiveReframe` | 想法校准 | CBT | 源自经典认知行为学派 |
| `releaseControl` | 放下控制 | ACT | 源自第三波认知行为疗法 |
| `selfCompassion` | 站回自己这边 | Self-Compassion | 源自自我同情与慈悲聚焦取向 |
| `boundarySupport` | 稳住情绪 | DBT | 源自第三波认知行为疗法 |
| `gentleRecovery` | 慢慢带回自己 | Behavioral Activation | 源自行为主义与 CBT 干预传统 |

### 2.3 非会员链路

- “继续深入”标题旁显示 Pro 标记。
- 5 张方法卡片以半透明和锁图标展示。
- 点击卡片或底部“Pro 深入分析”进入现有 Pro 购买页。
- 当前权限判断复用 `ProSubscriptionService.hasProFeatureAccess`。

说明：当前 Pro 限制主要由客户端控制。智能体接口上线后，服务端也应校验用户权益，不能只依赖客户端按钮限制。

### 2.4 深入分析结果页

新增独立深入分析结果页，页面结构为：

1. 方法名称大标题。
2. 专业方法名称和理论来源。
3. 方法概述。
4. “你真正卡住的地方”。
5. “更贴近你的理解”。
6. “现在先做这一件小事”。
7. “一句陪你站稳的话”。

点击“完成”后不会立刻退出整条记录，而是把结果返回 NVC 结果页。

### 2.5 深入分析结果回写

- 已完成的深入分析以紧凑模块追加在 NVC 的“行动 Tips”下方。
- 点击紧凑模块可重新打开完整深入分析结果。
- 同一条记录可以保存多种不同方法的分析。
- 同一种方法再次分析时更新原结果，不重复堆叠。
- 多种方法按生成顺序纵向排列。

## 3. 客户端当前的数据实现

### 3.1 深入分析数据结构

客户端新增 `DeepAnalysisResult`：

```json
{
  "type": "selfCompassion",
  "title": "站回自己这边",
  "methodLabel": "Self-Compassion",
  "theorySource": "源自自我同情与慈悲聚焦取向",
  "overview": "方法概述",
  "stuckPoint": "你真正卡住的地方",
  "groundedUnderstanding": "更贴近你的理解",
  "oneSmallStep": "现在先做的一件小事",
  "steadySentence": "一句陪你站稳的话",
  "analyzedAt": "2026-06-07T10:00:00.000Z"
}
```

### 3.2 本地临时存储

当前为了不阻塞页面和产品验证，使用本地方案临时实现：

- 存储位置：Hive `settings` box。
- Key：`deep_analysis_v1_<recordId>`。
- Value：`DeepAnalysisResult` JSON 数组。
- 新记录创建成功并取得 `recordId` 后写入。
- 编辑已有记录时同步更新本地深入分析。
- 删除记录时同步删除对应本地数据。
- 重新打开记录时按 `recordId` 恢复结果。
- 兼容早期本地单条 JSON 对象格式，并自动按单元素数组读取。

### 3.3 当前限制

- 换设备后无法恢复。
- 卸载 App 或清空本地数据后无法恢复。
- 登录后的云同步不会携带深入分析结果。
- 同一账号在多设备上的深入分析状态可能不一致。
- 如果服务端记录被其他设备删除，本地独立数据需要依赖客户端后续清理。

这套 Hive 逻辑是**服务端能力上线前的临时兜底**，不是最终云同步方案。

## 4. 智能体当前进展

深入分析智能体目前处于“产品结构和输出 Schema 已确定，智能体尚未配置”的阶段。

目前已经确定后续会提供两类智能体能力：

1. **意图分类智能体**：根据用户原始记录和 NVC 结果，从 5 种方法中判断并返回推荐方法。
2. **深入分析智能体**：根据用户选择的方法生成对应的深入分析正文。

这些智能体会在后续提供和配置。五种方法最终使用一个统一智能体加方法参数，还是拆为多个独立智能体，目前不在客户端代码中预设。

### 4.1 当前实际运行方式

- 推荐方法：当前由客户端关键词规则临时选择；后续由意图分类智能体返回。
- 深入分析正文：当前由客户端固定模板临时生成；后续由深入分析智能体返回。
- 网络请求：无。
- 智能体 Prompt：未接入。
- 模型、工作流、Token、Project ID：未配置。
- 服务端智能体代理接口：未实现。

因此，当前页面适合验证流程、视觉和字段结构，但不能用于验证真实分析质量。

### 4.2 当前关键词推荐仅为占位逻辑

客户端目前大致按以下信号做推荐：

- 自责、能力否定、失败感：Self-Compassion。
- 人际冲突、沟通、边界：DBT。
- 疲惫、麻木、身体耗竭、快乐下降：Behavioral Activation。
- 反刍、失眠、控制、放不下：ACT。
- 其他情况默认：CBT。

后续应由已经规划的意图分类智能体替代，客户端只负责展示智能体返回的推荐类型。

## 5. 服务端需要补齐的能力

服务端工作建议拆为“推荐与生成”和“结果持久化”两部分。

### 5.1 接入意图分类智能体

推荐方法将由后续提供的意图分类智能体判断。为了让 NVC 结果页打开时立即显示推荐项，服务端需要负责调用该智能体，并向客户端返回稳定、受约束的分类结果。

可以在现有 NVC 分析结果中增加可选字段：

```json
{
  "recommendedDeepAnalysisType": "selfCompassion",
  "deepAnalysisRecommendationReason": "记录中出现了明显的自责和自我否定"
}
```

`recommendedDeepAnalysisType` 只允许以下枚举：

```text
cognitiveReframe
releaseControl
selfCompassion
boundarySupport
gentleRecovery
```

推荐原因当前可以只用于日志和调试，暂不一定展示给用户。

如果意图分类智能体与现有 NVC 智能体是两套独立工作流，服务端可以在 NVC 请求内部串联调用后一起返回；也可以新增独立分类接口。前一种方式客户端体验更连贯，后一种方式服务拆分更清晰，但会增加一次请求和等待。

### 5.2 接入深入分析智能体并新增生成接口

五种方法的分析正文将由后续提供的深入分析智能体生成。建议由服务端代理智能体调用，避免把智能体密钥和工作流配置放在客户端。

建议接口：

```http
POST /api/v1/analysis/deep
Authorization: Bearer <access_token>
Content-Type: application/json
```

请求示例：

```json
{
  "recordId": "record-id",
  "type": "selfCompassion",
  "transcription": "用户原始记录",
  "nvc": {
    "observation": "事实观察",
    "feelings": [
      {
        "feeling": "焦虑",
        "intensity": "high"
      }
    ],
    "needs": [
      {
        "need": "支持",
        "reason": "用户正在承担较多压力"
      }
    ],
    "request": "行动 Tips",
    "insight": "NVC 洞察"
  },
  "locale": "zh-CN"
}
```

响应建议直接使用客户端已实现的结构：

```json
{
  "type": "selfCompassion",
  "title": "站回自己这边",
  "methodLabel": "Self-Compassion",
  "theorySource": "源自自我同情与慈悲聚焦取向",
  "overview": "帮助你把责任与自我否定分开，在困难里重新站回自己这一边。",
  "stuckPoint": "你真正卡住的地方",
  "groundedUnderstanding": "更贴近你的理解",
  "oneSmallStep": "现在先做的一件小事",
  "steadySentence": "一句陪你站稳的话",
  "analyzedAt": "2026-06-07T10:00:00.000Z"
}
```

服务端需要处理：

1. 校验登录状态。
2. 校验 `type` 枚举。
3. 校验 Pro 权益；无权限返回明确错误，例如 `PRO_REQUIRED`。
4. 根据 `type` 调用后续提供的对应分析智能体，或调用统一智能体并传入方法参数。
5. 强制智能体返回结构化 JSON。
6. 对缺失字段、超长内容和非法 JSON 做解析与兜底。
7. 设置超时、重试、限流和可观测日志。
8. 返回稳定错误码，客户端不直接展示模型原始错误。

### 5.3 深入分析结果云端存储

建议在 Record 模型中增加可选数组字段 `deepAnalyses`：

```json
{
  "deepAnalyses": [
    {
      "type": "selfCompassion",
      "title": "站回自己这边",
      "methodLabel": "Self-Compassion",
      "theorySource": "源自自我同情与慈悲聚焦取向",
      "overview": "方法概述",
      "stuckPoint": "分析结论",
      "groundedUnderstanding": "理解结论",
      "oneSmallStep": "行动建议",
      "steadySentence": "支持性表达",
      "analyzedAt": "2026-06-07T10:00:00.000Z"
    }
  ]
}
```

需要同步修改：

1. Record 创建接口接收并保存可选 `deepAnalyses`。
2. Record 更新接口接收并保存该字段。
3. Record 列表和详情接口返回该字段。
4. 全量快照和增量同步返回该字段。
5. 删除 Record 时一并删除其深入分析。
6. 旧记录允许字段为 `null`、缺失或空数组。
7. 旧客户端发送的 payload 不包含该字段时，不应误清空已有深入分析。

同一种方法建议按 `type` 执行 upsert，不同方法允许并存。并发更新时建议以服务端记录版本或 `updatedAt` 处理冲突，避免多设备互相覆盖。

### 5.4 生成与保存的职责建议

推荐采用以下顺序：

1. 客户端调用 `/api/v1/analysis/deep` 生成结果。
2. 服务端返回结构化结果。
3. 客户端展示结果，用户点击“完成”确认。
4. 客户端通过 Record 更新接口保存确认后的 `deepAnalyses`。

这样可以避免用户只是打开预览，就把未确认结果直接写进记录。

如果服务端希望生成即保存，也需要明确返回最终 Record 版本，并处理用户退出、重试和重复请求的幂等问题。当前客户端交互更适合“生成”和“保存”分开。

## 6. 服务端完成后客户端还要做的工作

服务端接口可用后，客户端需要继续完成：

1. 在 `OceanApiClient` 或对应小接口中增加深入分析生成请求。
2. 把生成请求放到 Repository/Bloc 链路中，不从页面直接调用 Dio。
3. 使用服务端推荐类型替换客户端关键词推荐。
4. 使用智能体返回内容替换客户端固定模板。
5. 将 `deepAnalyses` 接入 `Record`、本地 `RecordModel` 和 `OceanRecordSyncMapper`。
6. 为 Hive `RecordModel` 追加新的字段编号，不复用或调整已有 `@HiveField`。
7. 将 `deep_analysis_v1_<recordId>` 中已有本地数据迁移到 Record 数据，并在云端保存成功后清理临时 Key。
8. 保留短期离线读取能力，避免服务端上线切换时用户本地结果丢失。
9. 增加接口解析、错误态、Pro 权限、重复请求和多设备同步测试。

## 7. 本地 Mock 能力

为了在没有真实 AI 配置时验证页面，v1.6 增加了仅 Debug 模式生效的环境开关：

```env
MOCK_API=true
MOCK_PRO=true
```

- `MOCK_API=true`：使用本地模拟转写和 NVC 分析，不请求真实 AI。
- `MOCK_PRO=true`：Debug 模式下临时获得 Pro 功能访问权。
- Release/Profile 构建不会因为这两个开关直接获得 Mock Pro 权限。

这两个开关只服务于本地开发和 UI 验收，不属于生产业务逻辑。
